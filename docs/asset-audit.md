### Already mitigated in code

A 69–89 MB file that begins streaming because a phone scrolled past it is not
acceptable. `ProjectVideo` in `src/pages/ProjectDetailPage.jsx` now:

* autoplays on desktop exactly as before (unchanged);
* on ≤860px renders the **poster only**, with no `src` on the `<video>` and
  `preload="none"`, and fetches the file only when the visitor taps play.

Verified: 0 `.mp4` requests on a 390px viewport with the film section scrolled
fully into view; 1 request after tapping play.

### Still recommended (needs the client, and the source masters)

These files are ~10× larger than they need to be for web delivery. Re-encoding
is the single biggest performance win available and does not change the design:

```sh
# 1080p desktop master, ~8–12 MB from ~85 MB
ffmpeg -i oscar-palace-walkthrough.mp4 -vf scale=-2:1080 -c:v libx264 \
  -crf 24 -preset slow -movflags +faststart -an oscar-palace-1080.mp4

# 720p mobile variant, ~4–6 MB
ffmpeg -i oscar-palace-walkthrough.mp4 -vf scale=-2:720 -c:v libx264 \
  -crf 26 -preset slow -movflags +faststart -an oscar-palace-720.mp4
```

`-an` is deliberate: the films play muted on the site, so the audio track is
pure overhead. `+faststart` moves the index to the front so playback can begin
before the file has finished downloading.

Once the variants exist, add `video_url_mobile` to the project entries in
`src/data/projects.js` and pick between them in `ProjectVideo` — the component
already knows the viewport.

## Frame sequences

`public/frames` (476 files, 60.5 MB) and `public/about-frames` (192 files, 13.8 MB)
are **all in use** — built with template literals, so a filename search alone
would have wrongly reported them as orphans. Do not touch them without reading
the note at the top of `src/components/Hero.jsx`.

The homepage sequence no longer blocks the reveal on all 476 frames; see
`BOOTSTRAP_FRAMES` in that file. Measured reveal on a throttled 4 Mbps
connection: **28.5s → 7.9s**, with 3.5 MB fetched before reveal instead of 9.7 MB.

A future win, if the client can re-export: half-resolution frames for ≤860px
viewports would cut the mobile sequence from ~60 MB to ~15 MB.

### Groups worth understanding before removal

* `/images/projects/oscar-palace-{1..5}.jpg`, `oscar-palace-gate.jpg` — an earlier
  Oscar Palace image set. The project now uses the `/images/oscar/**` folders.
* `/images/projects/{02,03,06,07,09,12}.jpg` and the per-project files there
  (`siddhayatan.jpg`, `oscar-fort.webp`, …) — thumbnails from before each project
  got its own folder. `08.jpg`, `04.jpg`, `05.jpg` in the same folder **are**
  still used, by `victoria-park`, so do not clear the folder wholesale.
* `/images/service-*.jpg` and `/images/services/*.png` — two generations of the
  services artwork. The `.jpg` files in `/images/services/` are the live set.
* Extra frames inside `/images/oscar/**` (`park-3/4/8`, `photo-10/12`,
  `entrance-5`, `amenity-4`) — surplus shots not currently in a gallery. Cheap
  to keep; useful if the galleries are extended.

## Reproducing this report

The audit is a plain reference sweep; re-run it after adding or removing assets:

```sh
# from the repo root — prints the same table this report was built from
grep -rFq "$path" src api plugins index.html   # is this asset referenced?
```

The full machine-readable classification of all files is regenerated by walking
`public/` and grepping the source, as described at the top of this document.
